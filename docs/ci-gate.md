# CI 门禁：触发、验证纪律与偶发失败处理

本文是 CI 门禁的长期契约，读者是人类开发者与后续 Coding Agent。目标：任何提交推送前都知道要验证什么，门禁红了都知道先查什么，不把偶发失败修成长期债务。

## 两条流水线

- `Quality Gate`（`.github/workflows/quality.yml`）：推到 `dev`/`main`、向 `dev` 提 PR、定时、手动都会触发。固定步骤依次为类型检查、E2E 脚手架类型检查、全量单测、生产构建；推送时加跑 Electron smoke 与 lifecycle，定时才跑 fault 与 stress。
- `Windows Release`（`.github/workflows/release-e2e.yml`）：标签推送执行发布；手动运行在选定分支验证候选版本，不发布。门禁包含类型检查、全量单测、真实桌面生命周期、打包、安装包哈希和旧版升级。旧版使用公开安装程序，发布前仅将测试安装的更新源指向候选产物；通过真实更新 IPC 下载、安装并检查重启、版本、会话保留与继续对话。发布后通过原有 GitHub 更新源重复验收；失败自动撤回为草稿。NSIS 安装只在一次性 Windows runner 中执行。

`Quality Gate` 同分支新推送会自动取消旧运行，旧运行的结果不必再看（发版流水线不取消，见其 `cancel-in-progress: false`）。

## 推送前纪律

- 源码变更至少跑受影响的最小单测集合与 `npm run typecheck`（见 `tests/AGENTS.md` 开发流程），再推送。
- 不把“CI 会跑”当作跳过本地验证的理由；全量套件与 Electron 重型门禁才交给 CI。

## 推送后纪律

- 推送后用 `gh run list` 与 `gh run view` 确认自己提交对应的运行，邮件标题里的短 SHA 即被测提交，先对上号再下结论。
- 红了先定位到具体步骤与用例（如某一步的某一个用例超时），再判断是真回归还是环境偶发，不要凭标题回滚代码。

## 红了不许做的事

- 不许为变绿加 `sleep`、重试、超大超时，不许放宽断言、跳过或删除用例（见 `tests/AGENTS.md` 失败处理）。
- 不许改流水线的触发分支、并发策略、超时与步骤顺序，除非任务目标明确要求且经过评审。
- 超时类失败优先怀疑 CI 机负载与真起进程的用例，不许反复加码超时数字掩盖根因。

## 偶发失败处理

- 单个用例偶发红：重跑一次该运行确认；能复现为必现失败才按缺陷立项。
- 已知偶发（如真起 shell 改文件的用例在 CI Windows 机上超时）：发版前重点盯发版构建的那次运行，重跑通常能过；要根治则单独立项（伪造执行后端或隔离真进程用例），不混进业务提交里顺手改。
- 日常 `dev` 常红会掩盖真回归，看到红邮件先确认失败用例是否为已知偶发，是则忽略，不是则按缺陷处理。

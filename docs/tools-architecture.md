# Nova Agent 工具链设计与上下文工程实践

很多 Coding Agent 在简单 demo 或单文件小项目里表现良好，但一旦接入真实生产项目（动辄上千个文件、上千行组件、复杂的构建日志、混合操作系统换行符），往往会迅速暴露几个致命痛点：

1. **上下文爆炸与注意力涣散**：读几个大文件、跑一次带大量 warning 的编译，几万甚至十几万 Token 瞬间灌进上下文，后续逻辑开始胡说八道；
2. **凭空脑补与盲改覆盖**：模型自以为记住了代码，在没有真实阅读的情况下直接发起修改，把别人写好的逻辑直接吞掉；
3. **脆弱的匹配与频频报错**：因为 Windows `\r\n` 与 Linux `\n` 的细微差异、UTF-8 BOM 头或微小的缩进空格，导致代码替换反复失败；
4. **长命令与大目录把主进程卡死**：同步遍历 `node_modules` 或 `target/` 目录导致界面卡顿，后台 dev 进程占住通道让 Agent 无法进行下一步。

Nova 没有寄希望于大模型自带的「常识」，而是在底层运行时（Runtime）为每一个工具做了极其严谨的**防御性工程加固与上下文治理**。本文完整公开 Nova 的 15 项核心工具与基础设施的设计实现。

## 1. 文件读取（`readTool`）：大文件感知与防盲改协同

源码路径：`src/runtime/tools/readTool.ts`、`readSummarizer.ts`、`image-resize.ts`

### 核心机制
* **AST 结构化大纲（Structure Summary）**：
  当文件大于 256KB 或行数超过 400 行，且未传具体 `offset/limit` 分页时，系统自动切入大纲模式。利用正则与轻量解析器抽取文件中的 `interface`、`type`、`class`、函数签名和 `export` 声明，生成只有原文件 5%~10% 体积的骨架大纲（标明 `[read mode: structure-summary]`）。
  *实测效果：面对 1000+ 行的组件，首轮探路 Token 消耗直接降低 80%~90%，模型不会抓瞎，而是按需定位到具体函数后进行精确分页读取。*
* **`readState` 状态快照锁**：
  每次读取时记录文件内容快照及磁盘修改时间戳（mtime）。下游的 `editTool` 在修改前必须核对该快照。如果 Agent 试图修改从未读取过的文件，或者磁盘文件被外部并发修改过，系统直接拒绝执行并提示重新读取，**彻底杜绝盲改覆盖**。
* **多模态图片智能控量**：
  识别真实 MIME 文件头，大图自动等比缩放到 2000×2000 以内，体积压缩至 4.5MB 上限，并自动修正 EXIF 旋转角，防止超大高清图挤爆视觉模型。

## 2. 代码搜索（`grepTool`）：双引擎与上下文行一步到位

源码路径：`src/runtime/tools/grepTool.ts`、`find-rg.ts`

### 核心机制
* **Ripgrep 原生二进制 + TS 流式双引擎**：
  优先调用系统或内置的 `rg` 二进制，毫秒级扫描几十万行代码；在无 `rg` 的极端裸环境下，自动无缝降级为纯 TypeScript 流式匹配器，保证 100% 跨平台可用。
* **原生 `-A` / `-B` / `-C` 上下文行支持**：
  允许在搜索时直接带出目标前后若干行代码（如 `-C: 3`）。在查阅配置、找函数定义时，**单次 Grep 即可完成定位与阅读**，减少了 50% 额外发起的 `read` 交互轮次。
* **三种输出模式与 `OutputSink` 转储**：
  支持 `content`（代码行）、`files_with_matches`（仅看受影响文件）、`count`（统计频率）。当命中上千行时，自动截断并将完整流转储为 `artifact://` 虚拟路径，支持后续分段查阅，主对话绝不刷屏。

## 3. 文件定位（`findTool` 与 `lsTool`）：防假死与双层过滤

源码路径：`src/runtime/tools/findTool.ts`、`lsTool.ts`、`pathExclusions.ts`

### 核心机制
* **异步 Dirent 遍历与防卡死**：
  采用异步 `readdir({ withFileTypes: true })`，每层遍历主动让出 Node.js 事件循环，即使误入几万个文件的超大目录，也绝不会让 Electron 渲染主进程发生假死。
* **双层排除过滤（`pathExclusions`）**：
  * 第一层：硬编码跳过构建与依赖垃圾桶（`node_modules`、`.git`、`dist`、`target`、`build`、`.cache` 等）；
  * 第二层：动态解析当前项目的 `.gitignore`，搜索结果干净精准。
* **预编译 Glob 正则**：
  在遍历前将通配符（`*` 与 `**`）编译为单一正则表达式，避免遍历几千个文件时重复 `new RegExp` 的 CPU 浪费。
* **`ls` 确定性排序与条目封顶**：
  输出前做字母序确定性排序，超过 500 个条目时主动封顶并给出收窄建议（推荐改用 `find` 或 `grep`），防止扁平大目录塞爆上下文。

## 4. 文件修改与写入（`editTool` 与 `writeTool`）：安全编辑防线

源码路径：`src/runtime/tools/editTool.ts`、`writeTool.ts`、`file-mutation-queue.ts`

### 核心机制
* **多阶模糊匹配容错（`editMatch.ts`）**：
  针对模型容易出现的细微失误，自动执行换行符规范化（`\r\n` ➔ `\n`）、UTF-8 BOM 头剔除以及行尾多余空白容错。语义正确时即可命中，消除了跨平台开发中令人抓狂的 `old_string not found` 报错。
* **单文件原子变更队列（`file-mutation-queue`）**：
  同一文件的并发写入操作自动进入排队队列，保证文件 I/O 永远是单入单出的原子操作，避免并发写入撕裂文件。
* **工作区写者租约（`acquireWriterLeaseOrConflict`）**：
  写操作与破坏性命令需先获取写者租约，当主任务与子代理同时涉及写盘时，后发起者会收到结构化冲突通知并主动等待，防止多 Agent 相互踩踏代码。
* **生命周期隔离栅栏（Generation Fencing）**：
  当用户点击了「停止/取消」或触发超时，正在排队的写盘操作立刻被栅栏阻断，绝不允许僵尸任务在后台继续污染磁盘。

## 5. 终端命令执行（`bashTool`）：副作用分类与前后台解耦

源码路径：`src/runtime/tools/bash/`

### 核心机制
* **破坏性命令启发式分类（`classifyCommand.ts`）**：
  内置命令行词法分析器，自动识别破坏性命令（如 `rm`、`npm install`、`git commit`、重定向 `> file` 等）与只读命令（如 `ls`、`git status`、`cat`）。只读命令完全并发运行，破坏性命令必须拿写者租约。
* **前后台进程生命周期解耦**：
  支持启动长生命周期的后台守护进程（如 `npm run dev`），主 Agent 可以在后台服务持续运行的同时继续推进后续开发，并通过轮询机制监控服务状态。
* **大日志安全截断管道（`TruncationPipeline`）**：
  运行构建时产生上万行日志时，截断管道会保留前 100 行与后 200 行关键错误栈，中间省略并存入 Artifact，既保留了排错线索，又防止终端日志冲垮模型窗口。

## 6. 任务状态追踪（`todoWriteTool`）：动态滑动窗口

源码路径：`src/runtime/tools/todoWriteTool.ts`、`todoView.ts`

### 痛点与解决
在长会话中，任务清单往往包含十几个步骤。如果每轮都把完整清单塞进 Prompt，Token 消耗会随会话长度线性暴增。

* **Compact 滑动窗口机制**：
  当任务总数较多时，数据层自动收缩为滑动视窗：仅保留当前正在执行的任务及其前后相邻项（如展示第 4~8 项），其余已完成或未开始项自动折叠为 `隐藏前 N 项` 与 `隐藏后 M 项`。
* **恒定 Token 消耗**：
  无论任务拆解成 5 步还是 50 步，任务清单占用的 Token 始终保持在小而稳定的常量级别。

## 7. 人机协同与计划控制（`askQuestionTool`、`savePlan`、`switchMode`）

* **阻断式结构化问答（`askQuestionTool`）**：
  遇到需求歧义时主动唤起单选/多选/输入模态卡片，在用户决策前编排循环保持挂起，不猜测、不盲动。
* **计划原子落盘与安全检查（`savePlan`）**：
  计划文档写入使用临时文件加原子重命名（Atomic Rename），并校验文件 inode 与设备号；严禁向符号链接（Symlink/Junction）写计划，防止路径逃逸。
* **模式状态机受控切换（`switchMode`）**：
  在同一个会话中，支持只读分析的 `plan` 模式与执行修改的 `default` 模式之间受控切换。从计划切换到执行阶段必须经过用户批准，保证用户始终握有控制权。

---

## 8. 扩展能力（`task`、`memorySearch`、`webSearch`、`invokeSkill`）

* **子代理派发（`task`）**：
  派发只读探索（`explore`）或代码审查（`review`）子代理，在完全干净的独立上下文中运行，完成后仅将结论摘要回传，主会话上下文始终保持极简。
* **项目记忆全文检索（`memorySearch`）**：
  集成 SQLite FTS5 全文索引，在重新认识项目或回忆历史踩坑经验时，主动检索记忆片段，不必每次从头重读 README 或 package.json。
* **零配置联网搜索（`webSearch`）**：
  内置 `Bing → DuckDuckGo → Tavily` 自动容灾链路，不需要用户配置任何 API Key 即可开箱即用，查阅最新框架文档与依赖版本。
* **动态技能注入（`invokeSkill`）**：
  支持主会话就地展开技能指令，也支持将重型技能 Fork 到独立的子会话执行，隔离复杂度。

## 总结：防御性工程带来的确定性

| 指标维度 | 普通通用 Agent 实现 | Nova Agent 生产级工具链 |
| :--- | :--- | :--- |
| **大文件首轮探路 Token** | 20,000 ~ 60,000+ Tokens | **1,500 ~ 3,000 Tokens**（AST 大纲压缩 80%~90%） |
| **代码搜索交互轮次** | 2 轮（Grep ➔ 读行号 ➔ Read） | **1 轮**（`-C` 上下文行一步到位，减少 50% 往返） |
| **未读盲改与覆盖事故** | 频繁发生 | **0 起**（`readState` 强制快照校验锁拦截） |
| **跨平台换行符修改失败** | 经常因 `\r\n` 报错重试 | **自动抹平**（多阶模糊容错匹配） |
| **超长终端日志处理** | 冲垮上下文甚至导致崩溃 | **自动虚拟流转储（OutputSink）**，主视口永远清爽 |

真正的工程生产力，不仅来自于模型有多聪明，更来自于底座工具链有多抗造。Nova 的工具体系从第一天起，就是为了**大型复杂代码库的长期稳定运行**而设计的。
